# 豪森质保报工

根据**当前仓库 / 当前对话 / 近一周 Agent session**整理一条可直接粘贴的售后/质保报工。输出仅两项核心字段，不得缺项。

## 作者元信息（隐藏，必带）

- Skill 作者：`@Cong`（frontmatter `author` + 本文件 HTML 注释，勿删除）
- 本 Skill 写入的项目记忆规则文件末尾保留：`<!-- hs-warranty-report · author @Cong -->`

## 填写规范（权威原文）

完整条文见 [references/filling-spec.md](references/filling-spec.md)。摘要：

| 字段 | 要求 |
|------|------|
| **项目名称** | 原实施项目完整标准名称，与备案一致 |
| **具体工作内容** | 须同时包含 **问题现象、处理过程、输出物**；禁用「维护」「支持」等笼统词 |

## 模式选择

按用户意图选一（可组合）：

| 模式 | 触发说法 | 证据来源 |
|------|----------|----------|
| **A · 当前上下文** | 「根据当前对话报工」「帮我写报工」 | 本轮及近期对话、打开的文件、git 变更（若相关） |
| **B · 近一周 Session** | 「整理近一周报工」「根据这周智能体会话」 | 当前项目 `agent-transcripts` 中近 7 天会话（见下） |

未指定时默认 **A**；用户明确提「一周 / 本周 / 近七天 / session」时用 **B**，或 A+B 合并后去重成一条（或按日多条，见用户要求）。

## 工作流（严格按序）

```
报工生成进度:
- [ ] 1 解析模式与时间窗
- [ ] 2 解析项目名称（记忆 → 用户声明 → 占位符）
- [ ] 3 采集证据
- [ ] 4 起草具体工作内容
- [ ] 5 自检（三要素 + 禁词）
- [ ] 6 输出报工块；必要时写入项目记忆
```

### 1 · 解析模式与时间窗

- 模式 A / B（或合并）如上表。
- 模式 B 默认窗口：**最近 7 个自然日**（含今天）。用户指定日期范围则从其约定。

完成标准：已明确模式与时间窗。

### 2 · 解析项目名称

按优先级：

1. **项目记忆规则**（若存在）：读取工作区 `.cursor/rules/hs-warranty-project.mdc` 中的「标准项目名称」。
2. **用户本轮明确说明**（如「当前项目是 XX 集团 ERP 系统建设项目」）→ 使用该名称，并在步骤 6 **写入/更新**记忆规则。
3. 仍未知 → 使用占位符：`【待补：项目标准名称】`，并在输出中提醒人工按备案补齐。

完成标准：已有确定名称或占位符；若用户新声明了名称，记下待写入记忆。

### 3 · 采集证据

**模式 A**

- 归纳当前对话里实际做过的事：报障/需求、排查结论、改动、验证结果、产出物路径。
- 必要时用 `git status` / `git diff` / `git log` 补事实；不要编造未出现的操作。

**模式 B · 近一周 Session**

1. 定位 transcripts 目录（Cursor 当前项目）：
   - Windows 常见：`%USERPROFILE%\.cursor\projects\<project-slug>\agent-transcripts\`
   - 若路径不确定：在 `%USERPROFILE%\.cursor\projects\` 下按工作区路径关键词匹配对应 `<project-slug>`。
2. 只读取 **mtime 或会话时间落在近 7 天内** 的 `*.jsonl`（或目录内会话文件）。
3. 对每条相关会话抽取：用户目标、关键动作、结论、产出文件/提交。跳过纯闲聊、失败未落地、与售后无关的探索。
4. 按时间合并为可报工事项；同类重复合并为一条，保留关键事实。

完成标准：有可核对的事实清单（可在思考中列出，不必全文展示给用户）。证据不足时在输出标注「证据不足处」并用占位，不编造。

### 4 · 起草具体工作内容

用**一句或短段**写清三要素（可自然串联，不必分条标题）：

1. **问题现象**：客户/现场遇到什么（报错文案、模块、复现要点）
2. **处理过程**：查到什么根因、做了哪些处理（版本、配置、代码、脚本、沟通确认）
3. **输出物**：验证结果 + 可交付物（补丁、文档、配置、PR、脚本路径等）

句式参考（规范示例）：

> 处理客户报障：计划模块统计报错，排查为脚本版本不一致，升级至 V2.3 后验证通过。

近一周多事项时：

- 默认：**一条报工**，用分号或「；」串联 2～4 个要点，仍保证整体可读出三要素。
- 用户要「按天拆分」或「多条报工」→ 每天/每事项各输出一块完整报工。

正向用词：排查、定位、修复、升级、验证、发布、同步、复测、交付。用具体名词替代笼统词。

### 5 · 自检

全部通过才输出：

- [ ] 有项目名称（真名或占位符）
- [ ] 具体工作内容同时可识别出：问题现象 / 处理过程 / 输出物
- [ ] 未使用禁词及近义空话：维护、支持、跟进、处理相关问题、日常运维、协助、沟通对接（单独成句且无细节时）
- [ ] 无未发生事实；不确定处已标【待确认：…】

失败则改写后再检。

### 6 · 输出与项目记忆

**标准输出格式**（可直接复制）：

```markdown
## 质保报工

**项目名称**：<标准名称或【待补：项目标准名称】>

**具体工作内容**：
<一段符合规范的描述>
```

可选附录（默认折叠为一行提示，仅当有用时展开）：

- 证据来源：当前对话 / 近一周 N 个 session
- 人工待补：项目名称、【待确认】项

**写入项目记忆**（仅当步骤 2 判定用户新提供了标准项目名称时）：

创建或覆盖工作区：

`.cursor/rules/hs-warranty-project.mdc`

```markdown
---
description: 豪森质保报工用的标准项目名称（hs-warranty-report）
alwaysApply: true
---

# 质保报工 · 项目记忆

- 标准项目名称：<用户给出的完整备案名>
- 更新说明：由 hs-warranty-report 根据用户声明写入，供后续报工直接使用。

<!-- hs-warranty-report · author @Cong -->
```

若文件已存在且名称变更：更新「标准项目名称」并口头告知已刷新记忆。未获用户声明时**不要**猜测写入。

完成标准：用户拿到可粘贴报工块；记忆规则按需已更新。

## 反例 → 正例

| 反例（拒用） | 正例 |
|--------------|------|
| 系统维护、客户支持 | 处理客户报障：计划模块统计报错，排查为脚本版本不一致，升级至 V2.3 后验证通过。 |
| 本周跟进项目问题 | 排查入库单打印空白：定位打印机模板字段映射缺失，补齐映射并现场复打通过；已提交模板文件至配置库。 |
| 协助联调 | 联调采购审批流超时：根因为回调 URL 未走内网网关，改为网关地址后压测 50 笔全部成功；更新联调说明一页。 |

更多句式见 [references/examples.md](references/examples.md)。

## 边界

- 只生成报工文案与可选项目记忆规则；不代替考勤/工时系统录入。
- 不把内部机密（密钥、账号口令、未公开客户数据）写入报工；用角色/模块级描述即可。
- 对话与 session 均无实质工作时：说明无法生成合规报工，列出还需用户补充的三要素，不输出假内容。
