# Diagnosing Bugs

先明确用户症状，建立尽可能准确的反馈信号，再验证假设。优先使用复现证据，不能把合理猜测或一次偶然成功当成根因确认。

## 上下文与边界

读取适用的 `AGENTS.md` 并遵循必读顺序，结合已有的 `docs/architecture.md`、`docs/conventions.md`、`docs/domain.md`、`docs/golden-rules.md` 和相关 ADR；`CONTEXT.md` 存在时作为补充。长文档按相关章节阅读，仓库要求全文必读时遵循要求。

缺少 Harness 时从日志、构建配置、调用链和测试建立上下文。仓库适用规则优先于本技能建议；业务文档与行为冲突时列出证据，不直接把任一方视为正确。

区分“定位原因”和“修复问题”：前者交付诊断证据，后者继续实施和验证。紧急恢复优先采用已授权、可回退的处置并保留证据，随后调查根因；恢复服务不等于根因消除。生产变更、压力注入或数据修改需核实已有授权与影响边界。

## 1. 定义症状与反馈

记录期望行为、实际结果、环境、触发输入、首次出现时间及近期变更。优先从现有材料获取，只追问影响定位的信息。允许先阅读代码以找到测试入口。

按场景选择有效路径，不必逐一尝试：

- 单元、集成或端到端测试，断言用户具体症状。
- HTTP/CLI 调用配合固定输入和结果断言。
- UI 自动化检查 DOM、控制台或网络。
- 脱敏请求或事件回放、最小服务测试程序。
- 已知好坏版本的差分；需要二分时使用隔离工作区，避免干扰用户改动。
- 必须人工操作时记录步骤与结果。有 Bash 交互终端可复制并调整 [人工复现模板](scripts/hitl-loop.template.sh)。模板依赖 `read`，不属于无人值守测试；没有 Bash 或交互终端时使用编号步骤和人工结果记录。

保存实际命令或人工步骤、输入、判定条件及关键结果。“没有崩溃”不能代替业务断言。区分已观察失败与仅具备检测能力但尚未触发失败。

尽量固定时间、随机种子、数据和外部依赖，缩短反馈时间。偶发问题记录样本量、失败次数与条件，在隔离环境按预算增加重复次数或负载；一次未复现不能判作修复成功。

## 2. 复现与缩小范围

确认出现的是用户报告的故障，再逐项减少无关输入、配置和调用步骤，每次保留相同症状断言。保留原始案例供最终验证；缩小到足以区分原因即可，不为形式上的最小化无限延迟定位或恢复。

无法复现时进入受限诊断：列出已尝试方式及限制，从调用链、日志、配置差异、历史变更或供应方响应继续形成可验证假设，明确区分“已确认原因”和“疑似原因”。需要缺失环境或数据时，给出最小所需材料与采集方法，完成不受影响的分析，不制造虚假红绿结果。

## 3. 验证假设

复杂问题列出少量有证据的候选原因，按可能性与验证成本排序；证据明确时不凑数量。每项写明依据、预测和可排除它的结果。例如：若重复订阅导致重复请求，清除多余订阅后同一次操作应只发出一次请求。

简要说明当前判断并继续可开展的检查。一次改变一个关键变量，保留探测结果；假设被否定后更新方向，不反复尝试同一修补。

优先调试器或针对性的现有日志。临时埋点使用唯一标识，限制字段与持续时间，不记录令牌、密码或完整敏感载荷；生产埋点应符合已有授权并能关闭。

性能问题先建立可比基线，保持数据规模、负载、缓存状态及测量条件可比，结合耗时分布、查询计划或 profiler 验证瓶颈。无法测量时标明性能收益尚未证实。

## 4. 修复与回归

仅在请求包含修复时实施。测试需覆盖真实故障路径；能稳定复现时优先观察测试失败，再应用最小修复并确认通过。绕开真正的多调用方、异步或事务关系的浅层测试不能算有效回归。

没有合适测试入口时说明原因，采用真实接口回放、集成环境验证或可重复人工验收。测试接缝改进应与问题直接相关，大规模架构重构作为后续建议。

复跑原始案例及仓库必跑检查。偶发或性能问题比较前后样本与条件，说明残余不确定性。环境阻塞时明确“已实现但未验证”的范围，不宣称问题已解决。

## 5. 清理与交付

检查并清理本次新增的临时埋点和试验文件，保留必要回归测试、复现材料及用户原有文件。根据仓库同步义务更新受到影响的业务、架构或运行文档。

交付包含症状、已确认原因或排序后的假设、关键证据、修复内容（如有）、实际验证和剩余限制。后续架构建议说明具体问题与收益，不依赖未提供的技能；仅在用户要求提交或发布时执行对应动作。
